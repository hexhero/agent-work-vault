# project-docs — 写项目文档

红线（什么时候读项目文件、改了要不要先问）在根目录 CLAUDE.md 的「项目」一节，这里是具体写法。写完跑 `bin/lint_vault.py`，格式不对它会报。

样板看 `examples/` 里的示例项目 demo（主文件、Design 和进度表、项目日志），`bin/setup.py --examples` 可以把它装进 `projects/`。

## 一个项目的四块内容

| 内容 | 回答的问题 | 放哪 | 写法 |
| --- | --- | --- | --- |
| **位置和资源** | 在哪、去哪查、用到什么 | 主文件 `projects/<项目>.md` | 改写，保持最新 |
| **坑** | 要注意什么 | 主文件的「红线」「坑」；多了拆到 `projects/<项目>/pitfalls.md` | 改写，过时的删掉 |
| **设计和进度** | 系统是什么样、为什么这样设计、计划做什么、做到哪了 | `projects/<项目>/design.md`、`design-<主题>.md` | 改写，只描述现在的方案 |
| **发生过什么** | 什么时候发生了什么 | `projects/<项目>/log.md`（项目日志） | 只追加，写了不改 |

**怎么判断放哪**：

- 动手时要照做的，进主文件。
- 描述「现在是什么样」、设计变了就要改写的，进 Design。
- 带日期、过了就不会再改的，进项目日志。
- 一个决定改了设计：项目日志记一条（日期、谁、原因），Design 直接改成新方案。
- 新结论取代了主文件里的旧内容：旧的挪进项目日志，主文件改成新的，不是在后面再加一段。

## 干完活怎么更新

干完项目上的活，不用事先问，按下面对一遍，改了在回复里说明改了哪个文件、改了什么。

| 发生了什么 | 更新哪里 |
| --- | --- |
| 地址、目录、容器、部署方式变了 | 主文件「位置」 |
| 多用或少用了一台服务器、一个库、一个内部 / 外部服务、一份凭据 | 主文件「资源」 |
| 踩了文件里没写的坑 | 主文件「坑」或 `pitfalls.md` 写结论；经过记项目日志 |
| 用户定了一件事、方案变了 | 项目日志记一条；涉及设计的同时改 Design |
| 上线了、发了版、一个里程碑做完了 | 项目日志记一条；`design.md`「阶段和进度」改状态；主文件「当前状态」必要时改一句 |
| 排查出一个结论 | 项目日志记一条（可以链到任务）；以后还会再踩的，结论同时写进「坑」 |
| 做了项目上的操作（发测试 / 生产环境、重启、改配置） | 项目日志记一条；每日任务日志的「事件」不重复记 |
| 这个项目的主文件还没按固定小节整理 | 顺手整理，见最后一节 |

## 主文件

**只记入口和去哪查**：项目迭代很快，写死的值容易过时还没人发现。会随代码变的值（服务清单、数量、端口、超时、版本、当前分支等）不抄进来，写成「去哪查」。核实日期只标在确实写了事实的地方。

**frontmatter**：只放稳定的入口，端口、版本等会变的值不放。

```yaml
---
type: project
name: demo                   # 等于文件名
description: "是什么、对外叫什么、在哪、怎么部署，一两句话"
aliases:                      # 别名，别人会怎么叫它
  - Demo
repo:                         # 仓库地址
  - https://github.com/...
hosts:                        # 部署主机 IP
  - 192.0.2.10
---
```

- `name` 和 `description` 的用法和 skill 的一样：`bin/projects.py` 只读这两项就能列出所有项目，用来判断手头的事属于哪个项目、该读哪个文件。所以 `description` 要写清**是什么、别人会怎么叫它、在哪**，带上能被搜到的关键词；不写版本和进度。用双引号包起来，里面不要再出现双引号。
- `aliases`、`repo`、`hosts` 供 [overview.base](../../overview.base) 用。
- `projects/` 下没有单独的索引文件，`name` 和 `description` 就是索引，在 Obsidian 里看 [overview.base](../../overview.base) 的「项目」视图。

**开头**：标题下面用几条列表写「简介」和一行「当前状态」（最多两句，每次整句替换，不追加；有 Design 的指向「阶段和进度」表）。

**固定小节**：按下面的顺序，节名固定，没内容的节不写。

| 小节 | 写什么 |
| --- | --- |
| `## 位置` | 仓库、各环境的主机、部署目录、容器、对外地址、怎么触发部署。多个环境用表格 |
| `## 资源` | 这个项目用到的资源，见下面「资源表」 |
| `## 按需读` | 同名目录里有哪些文件、做什么事的时候读哪个。有同名目录就要有这张表 |
| `## 去哪查` | 会变的值去哪条命令、哪个文件、哪张表、哪个接口查 |
| `## 怎么做` | 发布、回滚、加一条配置这类操作的步骤概要 |
| `## 红线` | 动之前必须先问用户的事。只写用户明确定过的，不自己加 |
| `## 坑` | 容易做错的地方，见下面「坑」 |
| `## 相关` | 相关的项目和 skill，用相对路径的 Markdown 链接 |

**太长就拆**：主文件超过约 16KB（lint 会警告），把只在某类事情上才用到的内容拆到同名目录的子文件，主文件只留每次都要用的。某个代码仓库自己的领域知识（厂商 API 的怪异之处等）最好写进那个仓库的 `AGENTS.md` / README。

### 资源表

一张表，三列：类别、资源、拿来干什么。类别用这几个：

| 类别 | 例子 |
| --- | --- |
| 服务器 | 各环境的主机、跳板机、开发机上的定时任务 |
| 数据库和存储 | 库、Redis、对象存储、主机上的数据目录 |
| 内部服务 | 公司自己的服务：网关、授权、Langfuse、平台 API、别的项目 |
| 外部服务 | 第三方：Entra、GitHub Actions、厂商 API、文档站 |
| 账号和凭据 | 用的是哪个账号、凭据放在哪。**只写指向的位置，不写值**，见下面 |
| 下游 | 依赖本项目的服务和工具，改接口前要看它们 |

- **资源和凭据都指向 `asset/`**：
  - **资源**：每一行链到服务清单（PROFILE「资产」里写的 `asset/` 下的文件）里对应的小节。资源的信息（地址、主机名、端口、目录）项目里可以写一份，方便干活时直接看；两边不一致时以 asset 为准，发现了就一起改对。别的项目写成项目链接。
  - **凭据**：项目文件里**只能写它存在哪**，不能写值，也不能写值的一部分。位置有三种写法：`→ config.yaml: <键>`（在 `asset/config.yaml` 里的）；主机上的文件路径和变量名（如「app01 的 `/data/.../secrets.env` 里的 `XXX`」）；代码仓库里的 `.env` 文件名和变量名。口令、token、API key、连接串里的密码都算凭据，Design、项目日志、pitfalls 里同样不能出现。
- 项目用到的资源服务清单里还没有的，把地址补进去（不用先问，改了说明）；新凭据的值只进 `asset/config.yaml`，按 CLAUDE.md「敏感信息」。

### 坑

- 只写**结论和怎么避开**，加核实日期。发现的经过、单号、当时的数字记进项目日志。
- 「红线」和「坑」分开：红线是必须先问用户的，坑是容易做错的。
- 修掉了、不再成立的直接删，在项目日志里记一条。
- 主文件超线时拆到 `projects/<项目>/pitfalls.md`：按主题分二级标题（授权、部署、某个子系统……），主文件只留每次动手都可能踩的几条，并在「按需读」表里写明什么时候读。`pitfalls.md` 超过约 32KB lint 会警告。

## Design

- **放什么**：目标和范围、架构、数据模型、接口、关键取舍和理由、还没开工的后续阶段、「阶段和进度」表。
- **只描述现在的方案**：不留「方案变更」「某天的决定」这类章节，带日期的决定和实施记录在项目日志。实施和方案的出入记在项目日志；出入是长期的，Design 也改成实际的样子。
- **按主题拆，不按时间拆**：`design.md` 是总览（目标、范围、架构、「阶段和进度」，并列出其他设计文件），一个子系统或一个阶段一份 `design-<主题>.md`。每份超过约 32KB lint 会警告，超了再按主题拆。
- **代码仓库里已有正本的设计不复制**，在主文件「去哪查」里写路径。
- 新建 Design 文件前先问用户。

### 阶段和进度

计划和进度记在 `design.md` 的「阶段和进度」一节，一张表，原地改写：

```markdown
| 阶段 | 范围 | 里程碑 | 状态 | 完成日期 |
| --- | --- | --- | --- | --- |
| 一期 | …… | 见下表 | 进行中 | |
| 二期 | …… | 待定 | 未开工 | |
```

- 在做的阶段可以再展开一张里程碑表；做完的阶段收成一行，细节在项目日志。
- 状态每变一次，项目日志记一条。主文件的「当前状态」只写一句并指向这张表。
- 没有分期计划的小项目不用为进度表建 Design，主文件那一句「当前状态」就够。

## 项目日志（log.md）

- **放什么**：谁哪天定了什么和原因、方案变更、里程碑、上线和发版记录、排查结论、实施和方案的出入、估算。只记系统和项目本身的变化；对外沟通（工单的评论和状态、聊天消息、邮件）不记在这里，记每日日志的「事件」。项目型任务的进展和事件**只记在这里**，每日任务日志里只留一行任务条目，不重复记（见 [daily-log](../daily-log/SKILL.md) 的「项目型任务」）。
- **粒度**：一件事一条，记到「某件事做完了 / 某功能上了测试、生产环境」。每次提交、每次重发这种流水不记，git 历史里有；同一天同一件事的后续，接在当天那条后面写，不另起一条。
- **格式**：按日期倒序，最新的在最上面，一天一个二级标题 `## YYYY-MM-DD`；下面每件事一条列表项，写清做了什么或定了什么、谁定的、原因和结果（版本、commit、单号）。lint 会查标题和顺序。

```markdown
---
type: project-doc
project: "[[demo]]"
---
# Demo 项目日志

## 2026-11-04

- `v1.2.3` 上测试和生产：修导出的时区（PROJ-123，`0082fef`）。经过见[任务详情](../../task/details/xxx.md)。
```

- **只追加**：写了的条目不改；后来发现写错了，加一条新的更正。
- **可以链到任务**，用相对路径（`../../task/details/xxx.md`、`../../task/YYYY-MM-DD.md`）。主文件、Design、pitfalls 和其他资料都不链到任务。
- 第一次要记时直接建，不用先问；建了就在主文件「按需读」表里加一行。
- 多个会话可能同时在写：改之前现读，只做局部追加，不整文件覆盖。
- **太长就按季度归档**：`log.md` 超过约 64KB（lint 会警告），把上个季度及更早的整段挪到 `log-YYYYqN.md`（如 `log-2026q4.md`，格式相同），`log.md` 只留当前季度。
- 某一天各项目都记了什么，用 `bin/day_summary.py [日期]` 看。

## 同名目录 projects/<项目>/

- 除了 `design*.md`、`log.md`、`pitfalls.md`，还可以放按需读的操作说明、产品方案、背景资料、脚本维护的发布记录等，由主文件的「按需读」表说明什么时候读。
- 只放代码仓库里没有正本的东西。某个任务的过程放 `task/details/`；定稿后长期有效的设计移进 Design，结论记进项目日志。
- 文件名用小写字母、数字和中横线 `-`，开头写 frontmatter：`type: project-doc`、`project: "[[项目文件名]]"`。
- 新建前先问用户，例外：项目日志 `log.md`、主文件超线时拆出的 `pitfalls.md`、脚本自动维护的文件（如 `<项目>/deploy-log.md`）。

## 新建项目

1. 先问用户。
2. 文件名用小写字母和中横线，照「主文件」一节写 frontmatter、开头和固定小节。
3. 跑 `bin/projects.py` 看新项目列出来了、`description` 读着清楚。

## 把旧项目文件整理成新结构

还没整理的主文件 lint 会汇总提示。**动到哪个整理哪个**，不专门批量做。步骤：

1. 读完主文件和同名目录，逐条判断属于四块里的哪一块。
2. 重写主文件：开头两条，然后按固定小节归位。位置和去哪查尽量用表格；从散在各段的文字里整理出资源表。
3. 带日期的经过、版本上线记录、已经修掉的问题，整理成项目日志的条目，按日期归到 `log.md`。
4. 主文件还超线，就把按主题的坑拆到 `pitfalls.md`。
5. 「红线」只搬用户明确定过的，没有就不写这节。
6. **技术事实一条不丢**：整理完对照原文过一遍；拿不准日期或归属的，在日志里照实写「日期没记」，不猜。
7. 跑 `bin/lint_vault.py`，在回复里说明拆成了哪几个文件、哪些地方是重写的、哪些拿不准。
