# daily-log — 写每日日志

红线（记不记、能不能勾完成）在根目录 CLAUDE.md 的「任务」一节，这里是具体写法。写完跑 `bin/lint_vault.py`，格式不对它会报。

## 先分清记在哪

每日日志只管「要做什么、做完没有」，是一张跨项目的待办清单，加上不属于任何项目的事。项目的知识和经过都记在项目那边，写法按 [project-docs](../project-docs/SKILL.md)。

| 内容 | 记在哪 |
| --- | --- |
| 任务条目（项目型和非项目的都是） | 每日日志「任务」 |
| 项目的进展、经过、排查结论、定下来的事 | 项目日志 `projects/<项目>/log.md` |
| 项目本身的变化：某功能上了测试 / 生产环境、发版、重启、改了配置 | 项目日志，每日日志不重复记 |
| 对外沟通：工单（ClickUp 等）的评论和状态、聊天消息、邮件（不管是不是项目的） | 每日日志「事件」 |
| 不属于任何项目的事：改本仓库的规则和 skill、查人事信息、调研、凭据 | 每日日志「事件」「日志」 |
| 会议回顾、非项目的查到的情况 | 每日日志「日志」 |

- 项目日志只记系统和项目本身的变化；沟通是关于人和单子的，留在每日日志。
- 「今天干了什么」用 `bin/day_summary.py` 看，它把各项目日志当天的条目和每日日志合在一起。

## 文件格式

- 每天一个文件 `task/YYYY-MM-DD.md`（当天日期），不存在就新建。
- 日期由文件名承载，条目里只写 `HH:MM`（24 小时制，精确到分钟）。时间按 PROFILE 里的时区取（如 `TZ=Asia/Shanghai date +%H:%M`），机器时钟和用户时区不一样时直接 `date` 会差几个小时。
- **多个会话会同时写同一天的日志**：改之前现读，只做局部追加或替换，不拿之前读到的旧内容整文件覆盖。提交前看 `git status` / `git diff --stat`，删除行数异常多就停下查；别的会话可能已经把你的改动一起提交了，这时确认 HEAD 里内容在就行，不改写历史。
- 文件分三部分，用三个二级标题分开，顺序固定：`## 任务`、`## 日志`、`## 事件`。哪部分当天没内容就不写那个标题。
- 提到仓库里的项目、skill 都写成相对路径的 Markdown 链接。

```
## 任务

- [/] 10:00 T-12 [PROJ-123 导出的时间少了 8 小时](https://app.clickup.com/t/xxx) #reporter/AliceChen
  - 项目：[Demo](../projects/demo.md)
- [ ] 11:00 T-13 整理报销单

## 日志

### 14:30 周会回顾

正文（列表或段落）。

## 事件

- 10:44 ClickUp PROJ-123 改成 dev done，加评论
- 15:20 改 daily-log skill 的事件规则，提交推送（2e6abf1）
```

## 任务

```
- [ ] 10:00 T-12 主题
- [/] 10:00 T-12 主题
- [?] 10:00 T-12 主题
  - 待确认：方案 A 还是 B
- [!] 10:00 T-12 主题
  - 卡在：等 xxx 发版
- [x] 10:00 - 11:30 T-12 主题
```

### 子行上限

一条任务下面的子行（「项目」行、「卡在」行、资料行、补充说明都算）最多 10 行，项目型和非项目任务一个标准，lint 会查。超了怎么办见下面两节。

### 内部编号

每条任务有一个内部编号 `T-N`，写在时间后面、主题前面，全局递增、不按天重置。它是任务的稳定标识（「把 T-12 改成 Block」），和工单号（如 ClickUp 编号）并存。

- **记任务时先取号**：跑 `bin/unfinished_tasks.py --next-id`，用它给的号。
- **编号跟着这一行不变**：改状态、改主题都不动编号；完成或取消后也保留，别处引用过的还能找到。
- **按编号查**：`bin/unfinished_tasks.py --id T-12`，已完成、已取消的也能查到。
- 子任务不编号。
- 多个会话同时记任务可能取到同一个号，`bin/lint_vault.py` 提交时会查重；撞了就把后提交的那条换成新取的号。

### 报告人

别人派的、或者做完要向某个人报告的任务，在任务行末尾加标签 `#reporter/<名字>`，如 `#reporter/AliceChen`。

```
- [/] 12:00 T-11 评估新报表方案要花多少时间 #reporter/AliceChen
```

- **名字的写法**：英文名去掉空格、每段首字母大写（Alice Chen → `AliceChen`），按 PROFILE「资产」里组织架构的名字写，同一个人始终一个写法；客户等公司外的人也照这个写法。
- **位置**：只写在顶层任务行的末尾，前面空一格；有 `→ [详情](…)` 的写在它后面，有类型标签（见「类型标签」）的写在类型后面。一条任务只写一个，子任务和子行里不写。
- **什么时候写**：记任务时知道是谁派的就写上，工单的报告人、聊天里提要求的人都算；用户自己起的任务不写。拿不准是谁就不写，不猜。
- **跟着这一行不变**：改状态、完成、取消都保留。
- **按报告人查**：`bin/unfinished_tasks.py --reporter AliceChen`；任务看板的卡片和详情里会显示报告人。

### 类型标签

任务行末尾可以加一个类型标签 `#type/<类型>`，说明这条任务是哪一类。现在只有一种：

| 标签 | 含义 |
|---|---|
| `#type/message` | 有人在聊天工具上找我（@我、私聊、叫我名字），要我回复或处理的任务；自动收件箱建的都带 |

- 和报告人标签一样写在顶层任务行末尾，两个都有时类型在前：`… → [详情](…) #type/message #reporter/BobLi`。一条任务只写一个类型，子任务和子行里不写。
- 类型是小写字母、数字和中横线。改状态、完成、取消都保留。
- 按类型查：`bin/unfinished_tasks.py --type message`；任务看板的卡片上会显示。

### 状态

| 写法 | 状态 | 什么时候用 |
|---|---|---|
| `[ ]` | 未开始 | 记下了还没动手 |
| `[/]` | 进行中 | 已经开始做 |
| `[?]` | Review | AI 做完了、或者做到一半要用户决策；下面写清等用户看什么 |
| `[!]` | Block | 卡住了、在等别人；下面写清卡在哪、在等谁 |
| `[x]` | 已完成 | 用户同意后才能勾 |
| `[-]` | 已取消 | 不做了 |

未开始、进行中、Review、Block 之间可以自己切换，改了在回复里告诉用户。卡住的原因解除后改回 `[/]`，把「卡在」那行删掉。


AI 处理任务时状态这样走，都不用先问：

1. **开始处理**：先把任务改成 `[/]` 进行中，再干活。
2. **要用户决策**（选方案、给权限、确认对外操作），或者**已经做完**：自动改成 `[?]` Review，下面加一行 `- 待确认：…`，写要用户决定什么，或者「已做完，等验收」加一句结果。回复里说明改成了 Review。
3. **用户给了决定、还要接着做**：改回 `[/]`，删掉「待确认」行。
4. **用户同意完成**：按「标记完成」勾 `[x]`。没同意就停在 Review，不自己勾。

Review 是等用户，Block 是等别人或外部条件，两个不混用。

### 项目型任务

链到某个项目的任务。

- 条目**只留一行**：状态、时间、内部编号、主题、工单号、报告人标签。
- 下面挂 `- 项目：[xxx](../projects/xxx.md)` 一行（`bin/unfinished_tasks.py -p` 靠它按项目筛选），Block 的再加「卡在」行，Review 的加「待确认」行。完成后「项目」行保留，不用改成在主题里写链接。
- **可以挂资料行**：做这条任务时要用到的资料，按用途分行挂在下面（如「照着做」「入口」「出问题时查」），一行一类，只放链接和一句说明，开工时不用再找。指向项目文件、Design、线上文档和页面；内容本身不抄过来。
- 不挂进展、经过、结论这类补充说明，进展和经过记到项目日志。子行超过 10 行就精简、把内容挪到项目那边，或者转成 `task/details/` 文档。
- 这条任务自己的过程（调查、方案比较、草稿）要留长文档时可以建 `task/details/`，条目上加 `→ [详情](details/xxx.md)`；长期有效的设计和结论仍然并进项目的 Design、项目日志或坑。

### 非项目任务

- 可以在条目下面补充说明。
- 子行超过 10 行时，直接转成 `task/details/` 文档（不用先问），条目只留一句话加 `→ [详情](details/xxx.md)`，转完告诉用户。
- 有详情文档的，条目只写一句话，细节放进文档。

### 记任务

1. 先跑 `bin/unfinished_tasks.py`（按项目看加 `-p`，按工单号看加 `--ref`）：这次的活如果是某条未完成任务的后续，提示用户关联到那条，更新原条目，不另起新条目。
2.用户说加才加。补记时开始时间写开始干活的时间；内部编号用 `bin/unfinished_tasks.py --next-id` 取；知道是谁派的就在行末加报告人标签（见「报告人」）。
3. 新增、拆分、合并任务时，都明确告诉用户加了 / 拆了 / 合了哪条，以及原因。
4. 同一件事的后续步骤（先记想法、再调研、再细化方案）算同一个任务：更新原条目。后续的内容，项目型的接着记项目日志，有详情文档的写进同一份详情文档。

### 标记完成

1. 做完后把任务改成 `[?]` Review，问用户这个任务能不能标记完成。
2.用户同意后，用 `bin/unfinished_tasks.py` 输出的文件和行号定位条目，勾上 `[x]`，补上结束时间（`开始 - 结束`）。
3.用户没同意之前，停在 Review。

## 事件

自动记，**不用问用户**，也不用在回复里提醒。我做了改变状态的操作就记一条；属于项目本身变化的记到项目日志，其余的记在这里，按时间顺序往下追加。

- 记在这里：改工单（状态、评论、依赖）、发聊天消息 / 邮件、改本仓库的规则 / skill / 文档并提交推送、存取或轮换凭据、新增或改动任务状态，以及其他不属于某个项目的状态变更。
- 记到项目日志：部署、发版、重启、改项目配置、项目上定下来的事。
- 不记：纯查询、读文件、跑只读脚本、草稿（没发出去的）、每次提交这种流水。
- 格式：`- HH:MM 做了什么`，一行一件事，写清对象和结果（commit 号、工单号）。不用复选框，不挂子列表。

## 日志

记下来备查、不用跟进状态的内容，如会议回顾、非项目的查到的情况。

- 每条用三级标题 `### HH:MM 标题` 开头，正文随意，但**不要用复选框**（`bin/unfinished_tasks.py` 会把复选框当成任务）。
- 日志不算任务，不用问是否完成。
- 项目相关的结论不写在这里，记到项目日志。

## 详情文档（task/details/）

- 项目型和非项目任务都可以建，创建前先问用户（上面「超过 10 行直接转」、后台自动化建的除外）。项目型任务的详情在 frontmatter 的 `project` 里写上项目。
- 文件名只能用小写字母、数字、中横线 `-` 和下划线 `_`，后缀 `.md`。
- 开头写 frontmatter，标题下面一行用 Markdown 链接写上任务日志：

```markdown
---
type: task-doc
project: []
log: "[[2026-10-13]]"
---
# 标题

> 任务日志：[2026-10-13](../2026-10-13.md)
```

- 项目型详情（frontmatter 的 `project` 不为空）里长期有效的设计和结论，任务做完时并进项目的 Design、项目日志或坑。
